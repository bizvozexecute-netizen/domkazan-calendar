# Стабильное первое открытие тестового каталога

Область изменения: только подготовленный T123 для страницы `311744409`, общий
модуль каталога и браузерные тесты. Публикация и изменение страниц не выполняются.

## Причины и исправление

Старый T123 ждал DOMContentLoaded, последовательно загружал два модуля и затем
начинал запрос каталога. При холодном сервере этот запрос дополнительно ждал
Tilda API (до восьми секунд). Одной параллельной загрузки оказалось недостаточно:
промежуточный живой прогон всё ещё не проходил пятисекундное ожидание карточек.

Новый синхронный bootstrap запускается прямо в T123, когда его элементы уже
доступны. Два независимых модуля и фоновая проверка контента загружаются вместе.
Начальный экран использует вложенный в HTML кэш только публичных метаданных,
подготовленный из Tilda. Нет дополнительного запроса к API после передачи кэша
в `DomKazanCatalog.mount`. Источник не становится второй CMS: правки делаются
на Tilda, а `/api/catalog` обновляет метаданные в фоне при каждом открытии.
Нетронутый экран может обновиться сразу; после взаимодействия пользователя
новые метаданные применяются при следующем переходе. Автоматический поиск из URL
тоже не пересоздаётся фоновым обновлением.

Если публичные метаданные не изменились, DOM вообще не пересоздаётся. Отдельная
регрессия сначала воспроизвела замену уже готовых карточек теми же данными; теперь
сохраняются исходные узлы и не возникает повторного события готовности. Холодный
старт проверяется с двумя управляемыми порядками ответа: API до модулей и после
них. Офлайн-фикстура убирает только сетевой preconnect к реальному домену;
продуктовый T123 и живой smoke его сохраняют. При сбое CI сохраняет снимок и
контекст именно синтетических startup-тестов для дальнейшей диагностики.

Диагностика Linux CI выявила ещё одну задержку: оба внешних JS уже скачаны,
но их глобальные модули отсутствуют до завершения постороннего defer-скрипта.
WebKit умеет откладывать явно async-скрипты до первого paint / DOMContentLoaded;
это подтверждается его [ScriptRunner.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/dom/ScriptRunner.cpp).
Bootstrap теперь добавляет динамические скрипты с `async=false`: они скачиваются
параллельно, выполняются в порядке вставки и не попадают в эту отложенную очередь.
Тест по-прежнему требует готовые карточки при заблокированном постороннем defer,
с прежними пятью секундами ожидания. Флаги движка и нативные API не меняются.

В кэше нет занятости, заявок или персональных данных. Базовые цены из публичных
описаний не авторизуют бронирование и не подменяют расчёт поездки. Каждый поиск,
календарь и POST заявки по-прежнему обращаются к серверу. Сбой фонового обновления
не ломает готовый каталог; при сбое загрузки модулей возвращается обычная Tilda.
Сетевые ожидания ограничены десятью секундами, есть ручной повтор.

При повторном живом прогоне встретился отдельный сетевой `Failed to fetch` уже
после готовности каталога. GET доступности теперь допускает только одну повторную
попытку при сетевом TypeError или HTTP 502/503/504 в пределах тех же десяти секунд.
Изменение условий отменяет обе попытки. Ответы 4xx, ошибки данных и POST заявки
автоматически не повторяются. Постоянная сетевая ошибка показывает понятное
русское сообщение вместо технического текста браузера. Тесты проверяют предел
попыток, отсутствие повтора 429 и отмену при изменении гостей.

Инструментирование WebKit обнаружило BODY ResizeObserver из
`tilda-menu-1.0.min.js`: он продолжал рассчитывать якоря скрытого меню при изменении
высоты каталога. На тестовой странице до DOMContentLoaded точному блоку меню
`rec4862082401` временно назначается штатный Tilda-атрибут `data-screen-max="0"`.
Проверка видимости Tilda не запускает этот ненужный наблюдатель. При ошибке или
destroy прежнее значение восстанавливается. Нативный ResizeObserver, функции
Tilda и глобальные обработчики ошибок не переопределяются; ошибки не фильтруются.
Раннее скрытие резервных блоков действует только для точных page/block ID и пути
тестовой страницы. На рабочем `/` bootstrap ничего не делает.

## Подготовка к отдельной публикации тестовой копии

```sh
node scripts/refresh-tilda-initial-catalog.mjs
node scripts/render-tilda-test-snippet.mjs https://domkazan-calendar-tilda-test-gatewa.vercel.app
```

Первая команда читает публичный Tilda API и сохраняет очищенные данные в
`data/tilda-catalog-initial.json`. Вторая создаёт
`integration/tilda-311744409-t123.html` внутри репозитория, а не в родительской
папке. JSON экранируется для безопасного включения в HTML. Тест сверяет этот
артефакт с генератором. Перед публикацией нужно обновить кэш и проверить diff.

Обновление одного JS на шлюзе не меняет старый последовательный T123. Для
включения исправления после ревью отдельно потребуются новый JS на тестовом
шлюзе и замена T123 **только тестовой страницы**, до DOMContentLoaded. Этот PR
сам ничего не публикует. Запуск из `load`/DOMContentLoaded уже поздний для
предотвращения инициализации старого меню. При изменении блоков Tilda нужно
перепроверить точные ID, границы T123 и механизм видимости.

## Воспроизводимые проверки

```sh
npm run typecheck
npm run lint
npm test
npm run build
npm run test:e2e
```

Новые тесты проверяют параллельный старт до завершения постороннего defer-скрипта,
единственный запрос метаданных, первое отображение при зависшем источнике,
сохранение ввода при обновлении, свежие данные следующего перехода, восстановление
Tilda и прежнего атрибута меню при сбое, отсутствие эффекта на рабочем пути.
Они входят в обычный CI, включая Chromium и WebKit, без сетевой зависимости от
Tilda. Сценарий с зависшим источником использует виртуальные часы, а не длинный sleep.

Для read-only проверки новых файлов на настоящем документе без публикации:

```powershell
$env:LIVE_TILDA_LOCAL_WIDGET='true'
$env:LIVE_TILDA_LOCAL_BOOTSTRAP='true'
$env:LIVE_TILDA_ALLOW_SYNTHETIC_REQUEST='false'
npx playwright test -c playwright.tilda.config.ts
```

Перехват касается только тестового HTML и JS в текущем браузере; поиск, календарь,
фотографии и видео используют настоящие тестовые сервисы. Границы T123 проверяются
до замены. Общая Playwright-фикстура применяет эти флаги и к пути поиска, и к
проверке видео: прогон новой версии не смешивается с опубликованным старым JS.
Для проверки опубликованного кода оба LOCAL-флага должны быть `false`.
Стандартное expect-ожидание остаётся пять секунд; увеличивать его или исключать
ResizeObserver-предупреждения для получения зелёного результата не нужно.
Метрика `domkazan:startup-to-ready` отражает работу от bootstrap до первого
каталога и не включает загрузку самого HTML. При перехвате JS она не измеряет
публичную CDN-доставку этих модулей. Числа и результаты прогонов фиксируются в PR.
Успешные проверки с подменой файлов не означают, что публичный стенд обновлён.
Перед передачей заказчику нужен полный успешный прогон опубликованного стенда;
тайм-ауты загрузки HTML, свежего поиска или внешнего плеера считаются сбоями
приёмки, даже если изолированные регрессии проходят.

## Совместимый патч безопасности при итоговой проверке

23 октября повторный `npm audit` и сборка обнаружили у установленного Next.js
16.4.0 три официальных advisory: GHSA-673q-mjm6-r5xr, GHSA-2464-fhr4-w9xw и
GHSA-p3m5-59mp-jv5r. Прежний нулевой аудит не описывает новое состояние registry.
Применён только патч Next.js 16.4.1 и его lockfile; Prisma и ESLint не обновлялись.
Основание: [официальное обновление Next.js](https://nextjs.org/blog/nextjs-security-update-october-14-2026).
Это изменение исходников, а не обновление работающих развёртываний. Оно требует
пересборки тестового Preview перед окончательной передачей; существующий шлюз
продолжает обращаться к старому Preview, пока отдельно не будет обновлён стенд.

Остаются внешняя скорость сети/HTML Tilda, CDN фотографий и Rutube. При отсутствии
связи начальный кэш описаний может устареть; доступность и итог заявки всё равно
не считаются подтверждёнными без сервера. Физический iPhone требует отдельной
приёмки. Схема БД и миграции не менялись; обновление Next.js ограничено патчем.
