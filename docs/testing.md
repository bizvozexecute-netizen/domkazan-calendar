# Тестовый стенд и эксплуатационные проверки

## Локальный запуск

Требуются Node.js 22.12+ и работающий Docker Engine/Desktop с Compose v2. В корне проекта:

```sh
npm run local:up
```

Открыть `https://localhost:8443/admin` и `/test-catalog`. Самоподписанный сертификат действителен 30 дней только для localhost; доверять ему можно только на собственном тестовом компьютере. Пароль тестового администратора — в `.local-test-credentials.json`. Файл `.env.local-test` содержит случайные локальные секреты и не перезаписывается повторным запуском. Эти файлы исключены из Git и Docker build context. Реальные контакты не вводить.

Стенд использует отдельный проект `domkazan-calendar-test`, постоянный том PostgreSQL и базу `domkazan_calendar_demo_test`. Никакие старые тома не удаляются. Восемь активных и один отключённый вымышленные дома имеют разные вместимость/районы/удобства, два соседних периода четырёх тарифов, ручные цены и закрытия относительно текущего дня. Клиентских записей в seed нет. Повторный seed не сбрасывает правки. Через год периоды нужно обновить в админке либо создать новый чистый тестовый том вручную.

Запуск: PostgreSQL healthcheck → одноразовый `prisma migrate deploy` → standalone Next.js healthcheck → HTTPS proxy и worker → seed. Ошибка миграции останавливает запуск приложения. При наличии старых пересекающихся `CONFIRMED` заявок новую миграцию нельзя применять до ручного устранения конфликта.

```sh
docker compose --env-file .env.local-test ps
docker compose --env-file .env.local-test logs --tail 50 app migrate telegram-worker
npm run local:down
```

Остановка сохраняет данные. `down --volumes` удаляет их — для обычного перезапуска эта команда не нужна.

## PostgreSQL backup и восстановление

```sh
npm run local:backup
```

В `backups/` появляются архив custom-format и SHA-256. Создание атомарное: сначала `.partial`, после проверки архива — финальное имя. Существующий файл не перезаписывается, права ограничены `umask 077`. Архив содержит все таблицы, включая миграции и заявки; он потенциально содержит персональные данные и секреты сессий. Каталог исключён из Git/Docker context. Для удалённого стенда нужны шифрование, отдельная копия вне сервера, ограничение доступа и согласованный срок хранения; автоматического удаления архивов нет.

Проверка восстановления не перезаписывает исходную базу:

```sh
docker compose --env-file .env.local-test run --rm restore /backups/ИМЯ-ФАЙЛА.dump domkazan_restore_check_test
docker compose --env-file .env.local-test exec -T postgres psql -U domkazan -d domkazan_restore_check_test -c 'SELECT count(*) FROM "House";'
```

`restore.sh` проверяет checksum, принимает только новое имя с суффиксом `_test` и отказывается работать с уже существующей базой. Применяется `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges`. Переключение приложения на восстановленную базу выполняется отдельно через `DATABASE_URL`; старую базу скрипт не удаляет.

Для автоматического сравнения восстановленных данных (нужны локальные `pg_dump`, `pg_restore`, `createdb`, `sha256sum`, `sh` и отдельный `TEST_DATABASE_URL`):

```sh
npm run test:backup
```

Проверка сравнивает все public-таблицы, историю миграций и определения ограничений, проверяет неизменность исходника и удаляет только собственную временную базу/архив. Это проверка восстановления одного database dump; роли и конфигурация всего PostgreSQL-кластера в архив не входят.

## Планировщик Telegram

Compose поднимает `telegram-worker` автоматически. Он получает только URL внутреннего endpoint и `TELEGRAM_RETRY_SECRET`; сам токен бота остаётся у приложения. Циклы выполняются последовательно с минутной паузой после завершения; таймаут вызова — 120 секунд. Каждый notification имеет атомарную 30-секундную аренду в PostgreSQL, HTTP-вызов Telegram ограничен 5 секундами. Параллельные worker не отправляют одну запись одновременно. При временной ошибке сохраняется backoff; после падения worker незавершённая аренда истекает. Возможен повтор сообщения после аварии между доставкой в Telegram и фиксацией `SENT`; ID заявки в нём тот же.

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` по умолчанию пустые. Для живого теста настроить отдельного тестового бота/чат в `.env.local-test` и пересоздать app/worker. Не использовать реальные данные клиентов. Worker пишет только результат цикла/HTTP-код, без URL с токеном, тела сообщения или контактов.

## Proxy, HTTPS и IP

`ops/nginx.conf.template` — конфигурация локального тестового proxy. Публикуется только `127.0.0.1:8443`; app и PostgreSQL доступны лишь внутри Docker-сетей, база подключена к internal-сети. Nginx завершает TLS 1.2/1.3, ограничивает тело до 16 KiB (форма дополнительно до 8 KiB), закрывает `/api/internal/`, отключает access-log и не кеширует ответы приложения. Cookie администратора на HTTPS имеет Secure/HttpOnly/SameSite=Strict.

Nginx перезаписывает Host, X-Forwarded-Host/Proto/Port, удаляет Forwarded/X-Forwarded-For/X-Real-IP и передаёт собственный `$remote_addr` в X-DomKazan-Client-IP вместе с секретом proxy. Приложение доверяет этому IP только при совпадении `TRUSTED_PROXY_SECRET`; иначе используется общий ограниченный bucket `unknown`, а не подставленный посетителем адрес. Не открывать app-порт в обход proxy. За дополнительным CDN нельзя слепо включать `real_ip_header`: сначала явно определить доверенные CIDR и политику перезаписи заголовков.

`APP_ORIGIN` задаёт канонический origin для CSRF и redirects, `TILDA_ORIGIN` — точный разрешённый origin каталога. `ALLOW_INSECURE_LOCAL_HTTP=true` допускается только для loopback при локальном браузерном тесте; на удалённом стенде нужны HTTPS и `false`. Для удалённого тестового сервера отдельно настроить домен/порты/доверенный сертификат и PUBLIC_HOST, соответствующий APP_ORIGIN. Шаблон localhost автоматически наружу не публикуется.

`node scripts/test-proxy.mjs` проверяет локальный Docker HTTPS endpoint: TLS, защищённые страницы, Secure-cookie, канонические redirects, закрытый retry endpoint и невозможность обхода IP-лимита подставными заголовками. Скрипт использует только вымышленные данные и не создаёт клиентских заявок.

## Персональные данные

PRIVACY_POLICY_URL обязателен, должен быть HTTPS и совпасть с адресом в форме. В заявке сохраняются время и URL согласия. `/test-policy` — только памятка вымышленного стенда, доступная при TEST_CATALOG_ENABLED=true и базе `_test`; это не юридический документ владельца. Для реального внедрения её необходимо заменить согласованной политикой и определить срок хранения/удаления заявок и архивов.

Публичные availability/requests/health API не возвращают клиентские данные. Контакты доступны только через авторизованную админку. В логах нет тел формы или ошибок Prisma с входными значениями. В тестовом каталоге отсутствуют реальные фотографии и описания Tilda. Браузерные traces и video отключены, чтобы не сохранять сессионные cookies; скриншоты содержат только синтетический стенд.

## Проверки и CI

```sh
npm ci
npm run db:generate
npm run typecheck
npm run lint
npm test
npm run test:integration
npm run build
npx playwright install --with-deps chromium
npm run test:e2e
npm run test:backup
npm audit --omit=dev
npm audit
```

Интеграция и E2E требуют отдельный TEST_DATABASE_URL с суффиксом `_test`, отличающийся от DATABASE_URL. E2E использует порт 3100, временные случайные пароль/сессию, 9 вымышленных домов и проверяет реальные HTTP/API/PostgreSQL взаимодействия в Chromium при десктопной и мобильной ширине. Созданные тестом заявки удаляются после сценария. Скриншоты — в `test-results/`.

GitHub Actions `.github/workflows/ci.yml` запускает TypeScript, ESLint, unit/DOM, интеграцию на временной PostgreSQL 16, production build, Chromium, backup/restore и аудит. Отдельная job собирает Dockerfile, запускает Compose с HTTPS, проверяет proxy и восстанавливает архив. Production-аудит блокирует CI; полный аудит явно сообщает известные dev-проблемы. Несовместимые `npm audit fix --force` не применяются. Workflow не публикует приложение и не меняет Tilda.
